# 为什么做 Open Cottage：在自己的环境里，把意图变成可验证的结果

> 写给关心「Agent 该怎么落地」的人。  
> 本文不是功能清单，而是回答三件事：**为何要做**、**设计上有何特色**、**为什么这么设计**。

---

## 1. 我们看到的问题

过去两年，聊天式 Agent 几乎无处不在。打开一个窗口，说几句话，模型给出一段看起来合理的回答——这件事已经不难。难的是下一层：

**把意图变成真实工作，而且让人敢用。**

现实里常见的落差是：

- 交付物停在对话摘要，而不是磁盘上的文件、表格、幻灯片、代码改动。
- 模型说「已完成」，用户却无法核对改了什么、漏了什么、能不能回滚。
- 为了「万能」，默认把 shell、裸脚本、任意网络访问交给模型——能力看起来很大，失败却不可解释，权限也不可控。
- 产品往往绑死在单一战场（例如只做代码仓库），办公、调研、网页自动化被当成另一套工具链。

于是出现一种尴尬：演示很炫，日常却不敢把重要文件夹交给它。

Open Cottage 的出发点很朴素——**不是再做一个更会聊天的窗口，而是做一个能在用户自己环境里把事做完、做清楚的工作台。**

一句话收束：

> **在你自己的环境里，把自然语言意图稳定地变成可验证的结果。**  
> （Trustworthy work completion in your own environment.）

---

## 2. 为何要开发本系统

### 2.1 工作发生在文件夹里，不在对话框里

多数知识工作的终点不是一段 Markdown 回复，而是：

- 一份可发的周报 / PPT  
- 一张改完公式的表格  
- 一次可 review 的代码改动  
- 一篇带来源的调研报告  
- 一组抓取与整理后的网页材料  

这些东西天然落在**本地目录**里。如果 Agent 只能聊天，用户还得自己复制粘贴、另存、对齐格式——那它只是加速了前半程，后半程的「落地与验收」仍然全靠人。

所以我们选择：**以本地文件夹为工作空间**，Agent 在其中读写，结果以真实文件交付，并在界面里预览、diff、审阅。

### 2.2 「能跑通」不等于「敢长期用」

企业和个人真正担心的不是模型聪不聪明，而是：

- 数据会不会被莫名上传或散落  
- 一次误删、误写能不能拦住  
- 出错后能不能定位是计划、工具还是验证出了问题  

因此「信任」必须是产品结构的一部分，而不是事后补丁。Open Cottage 把 **本地优先、策略审批、暂存审阅、可核对交付** 放进主路径：Key 可留在浏览器侧，工作区数据落在 `.cottage/`，破坏性操作可问人，写入可先暂存再应用。

### 2.3 通用任务需要平台，而不是堆更多原语工具

「通用」很容易被误解成「给模型一把万能钥匙」。那条路短期出活快，长期却把不确定性和解释成本甩给用户。

我们更想要的是：同一套**编排、策略、验收、人机交互**轨道，服务多种任务类型；具体领域能力（办公、编程、PDF、联网研究……）以**可插拔的能力包**装上，而不是每做一个场景就造一个新 Agent。

换句话说：**通用的是平台纪律，多样的是领域能力。**

## 3. 设计特色：几条刻意的选择

### 3.1 浏览器是第一层容器——交互与信任中心在人这边

Agent **住在浏览器里**：编排、策略、验收、确认框、预览与历史，都在这一层完成。本地伴随服务（Cottage Service）负责搜索、抓取、无头浏览器等「能力平面」，而不是把 Agent 本体挪到后台、人只当旁观者。

这样选，不是因为浏览器算力最强，而是因为它天然具备：

- 人看得懂的 UI（diff、预览、审批）  
- 可控的权限边界（文件夹授权、Worker、策略闸门）  
- 清晰的扩展路径（MCP、伴随服务、可选代理）

**人是驾驶员，Agent 是容器，LLM 是大脑。** 设计目标是让人好开、好看、好信任——不是让大脑踩油门更爽。

### 3.2 方便人，而不是方便 LLM

这是 Open Cottage 最核心的产品偏见。

| | 方便 LLM（我们刻意避免当默认） | 方便人（默认路径） |
|--|--|--|
| 工具 | `runShell("……")` 万能拼装 | 语义化工具：写文档、改表格、分析影响…… |
| 失败 | 一坨 stderr | 结构化错误 + 可理解的下一步 |
| 结果 | 「我执行完了」 | 交付物 + diff + 可回滚 / 可丢弃 |
| 权限 | 模型自行决定 | Policy 审批 + 能力白名单 |
| 扩展 | 再注册二十个原始工具 | 注册一个封装好的能力包 / 服务连接 |

原始脚本类能力可以存在，但定位是**逃生舱**，不是高速公路。默认该走的是：语义化工具 → 策略闸门 → 暂存/预览 → 人确认。

### 3.3 本地优先，数据跟着工作区走

打开一个文件夹，就等于划定 Agent 的世界边界。会话、索引、附件、工作区配置等落在目录内的 `.cottage/`，随工作区备份与迁移；域名级设置与 API Key 则分层存放，避免「所有秘密都捆在一处说不清」。

这不是情怀，而是信任模型：**权限在用户，数据在用户控制的边界内。**

### 3.4 Platform Core + Capability Pack

平台核心只做与任务类型无关的事：能力注册、策略引擎、验收、追踪、暂存与交付管线；更严格的计划闸门属于保留的治理能力。
编程、办公、PDF、深度研究等是 **Domain Pack**：需要时打开，注入工具与领域提示；不需要时保持安静，降低噪声与误用面。

「通用」因此有边界：**任务类型可以多样，但「完成 + 验证 + 本地控制」这三件事不可妥协。**

### 3.5 先计划、可审批、可核对

危险或外部调用前，倾向先产出可审视的计划；工具按风险分级，破坏性操作可弹审批；写入可走暂存，看过再落盘。任务结束追求的是结构化的「做完证据」，而不只是模型自述。部分更严格的计划治理与编排能力当前仍未对用户开放，发布前需以产品文档为准。

产品气质也因此偏克制：界面不为炫技堆卡片，而是让风险、改动、交付尽量**看得见**——因为看不见的「智能」，很难被信任。

## 4. 为什么这么设计（设计背后的取舍）

### 4.1 为什么不是「再做一个代码 IDE Agent」

代码助手已经很强，但大量真实工作发生在文档、表格、调研与流程自动化上。若平台从第一天就绑死在仓库场景，办公与研究只能永远是附属插件。

Open Cottage 反过来：**主战场是任意本地工作区**；编程是其中一个深度能力包，而不是唯一叙事。核心承诺不是「改对某一行代码」，而是「把这件事做完，并且能证明做完了」。

### 4.2 为什么坚持语义化工具，而不是默认 shell

给模型 shell，等于把操作系统的不确定性外包给概率模型。演示时很自由，生产时却最难审计：改了什么文件？为什么删了这个？stderr 里哪一行才是根因？

语义化工具把「合法操作目录」收束成人话 API，失败形态与权限边界也更清楚。扩展时优先封装服务与能力包，而不是无限增加原语——这是在用工程纪律换长期可维护的信任。

### 4.3 为什么 Agent 不整体下沉到本地服务

本地服务能力强，但一旦执行中心离开浏览器，人机交互容易沦为「事后看日志」。我们选择相反结构：

- **控制平面在浏览器**：人随时能理解、能打断、能验收  
- **能力平面在伴随服务**：需要系统权限或重执行时再调用  

这样扩展不会牺牲「人在回路」的默认体验。

### 4.4 为什么能力默认关闭、按包启停

同时打开所有工具，会让模型可选动作爆炸，也让用户说不清「这次它到底被授权了什么」。领域包默认关闭、按任务打开，是在用产品约束换可控性：少即是清晰，清晰才可审。

### 4.5 为什么把「可验证」写进 North Star

如果「完成」只靠模型口头确认，平台无法迭代，用户也无法建立肌肉记忆式的信任。diff、暂存、审批、交付清单、追踪回放——这些机制表面是功能，实质是在定义：

**什么叫做完，以及做完之后人如何复核。**

没有这一层，Agent 永远停在演示品。

---

## 5. 我们刻意不做的事

为了把上面的特色守住，有些诱惑需要明确拒绝：

- **不为了「看起来全能」默认开放无审批 shell。**  
- **不把 Agent 本体桌面化成黑盒后台进程，只留一个薄 UI。**  
- **不把所有场景塞进同一个永不关闭的巨型工具箱。**  
- **不满足于「对话里说完成了」而无文件级证据。**

这些「不做」，和「要做」同样重要。

---

## 6. 写在最后

Open Cottage 仍在早期（`0.x`），能力包与平台核心会持续演进。但方向已经定了：

它不是另一个聊天窗口，而是一个**以本地文件夹为边界、以浏览器为人机与信任中心、以可插拔能力包扩展领域、以可核对交付为终点**的 Agent 工作台。

如果只记住一句：

> 我们做它，是因为工作发生在你的环境里；  
> 我们这样设计，是因为只有「方便人、可核对、可审批」的 Agent，才值得长期托付。
